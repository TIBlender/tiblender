# Fidelity to the Paper

This table maps every paper section describing the TIBlender system design
to the module(s) that implement it, with an honest status and the concrete
deviation, if any. **Status**:

- **implemented** — matches the paper's design; only the LLM provider/model
  identity differs (see the LLM row).
- **simplified** — the mechanism is present but reduced in scale, fidelity,
  or coverage.
- **recomputed** — an evaluation result recomputed from the released
  dataset rather than by running the pipeline.
- **not included** — out of scope for this repository.

The pipeline code does not re-run the paper's 31-day deployment. The
deployment's evaluation results (effectiveness, baseline, human-validation
and ablation numbers) are recomputed from the released dataset by
`evaluation/run_evaluation.sh`. For running and inspecting the pipeline
itself, the repository ships a small, anonymized, offline-deterministic
fixture set.

| Paper section | Module(s) | Status | Deviation |
|---|---|---|---|
| §III-B Step 1 — Adaptive Collection, X and Reddit | `collectors/x.py`, `collectors/reddit.py`, `collectors/base.py`, `collectors/http.py`, `collectors/keywords.py`, `dynamic_queries.py` | simplified | Official APIs only. X needs a paid Basic-tier bearer token (no recent search on the free tier). Dynamic (trend-adapted) queries target `x`/`reddit` only, the two keyword-search platforms; `config/x_users.txt` ships empty. The deployed system also feeds these keywords to Telegram/Discord discovery, which is outside this repository. |
| §III-B Step 1 — Adaptive Collection, Discord | `collectors/discord.py` | simplified | Collects exhaustively from already-joined guilds (text/announcement channels, `after` watermarks anchored at the oldest unseen message), capped at 300 messages/channel/cycle. Prefers a user-account token over a bot token (see `docs/CREDENTIALS.md`). Discovering and joining servers is an operational, analyst-verified task outside this repository; `config/discord_guilds.txt` optionally narrows the run. |
| §III-B Step 1 — Adaptive Collection, Telegram | `collectors/telegram.py` | simplified | Collects exhaustive incremental history (per-channel `min_id` watermarks, oldest-first paging, FloodWait backoff) from `config/telegram_channels.txt` or every joined channel/supergroup. Uses Telethon (MTProto user session), since the Bot API cannot read arbitrary channel history. Channel discovery and joining are operational tasks outside this repository. |
| §III-B Step 1 — Preprocessing (rule filters, short-text discard, OCR merge) | `collectors/preprocess.py` | simplified | OCR is optional (`pytesseract`); bundled fixtures carry `attachments[].ocr_text` through the same merge path even without it installed. |
| §III-B Step 1 — Post normalization + verbatim IoC extraction | `normalization.py`, `iocs.py`, `llm.py`, `language.py` | implemented | Offline/heuristic path reproduces the paper's `Non-threat post:` judgment deterministically; such reports are marked `metadata.generation_mode=offline_deterministic`. The corpus is multilingual (Japanese, Korean, Russian, Chinese, Arabic); post text a report publishes as source evidence stays in its original language, exactly as the released dataset does, while everything the pipeline writes about it is English (see the Step 5 row). |
| §III-C Step 2 — Campaign-level clustering (IoC-Jaccard + embeddings + semantic absorption + HDBSCAN) | `clustering.py` | simplified | Default embedding backend is deterministic 384-d hashing, not the paper's bge-large-en-v1.5 (1024-d); the `bge_large` backend is an optional extra, falling back to hashing automatically. Thresholds (`τ_J=0.25`, `τ_abs=0.75`, `min_cluster_size=3`, `min_samples=2`, `ε=0.08`, `θ_sev=MEDIUM`) match the paper. |
| §III-D Step 3 — Multi-Perspective Investigation (planner, 4 perspectives, focus selection, pivoting, confidence aggregation) | `investigation.py`, `perspectives.py`, `context.py`, `tools.py`, `tool_fixtures.py`, `tools_social.py` | simplified | Pivot depth is 1 hop (not deeper chained pivoting). Clusters and their perspective agents run in two `ThreadPoolExecutor` pools (`TIBLENDER_CLUSTER_WORKERS=4`, `TIBLENDER_PERSPECTIVE_WORKERS=4`) instead of the paper's 32-worker process pool, with no per-cluster 600 s limit. **Confidence scoring** follows the paper's three rules (see `PIPELINE_OVERVIEW.md`'s Context Aggregation Confidence Rules for the mechanism), deviating from the deployed system in three specifics: source counting is per-post/per-tool-answer here versus per-evidence-type there, and a single-source Direct indicator scores LOW here versus MEDIUM there; the shared-hosting `+1` requires a link to a known-malicious domain, and an IP with more than `TIBLENDER_PIVOT_MAX_RESOLUTIONS_PER_IP=5` resolutions drops its co-tenants with no tier change, where the deployed system disables the check entirely or scores a crowded address LOW; contradictions lower one tier and are never cancelled elsewhere. `TIBLENDER_PASSIVE_DNS_LIMIT=20` matches the cap the bundled recordings were captured under, so replay truncates nothing. |
| Appendix — Implementation Details of RL-Guided Investigation (MultiAction DQN, BC, reward, replay) | `rl/features.py`, `rl/network.py`, `rl/reward.py`, `rl/replay.py`, `rl/trainer.py`, `rl/policy.py`, `rl/actions.py`, `rl_policy.py` | simplified | Structurally faithful: numpy MultiAction DQN, 320-d state, 19 actions, 256×256 LayerNorm/ReLU/Dropout encoder, four heads, behaviour cloning then DQN fine-tuning, replay buffer (capacity 10,000, training starts at 1,000 transitions), ε 1.0→0.01 decay 0.9. The bundled offline demo is small-scale — its three cycles accumulate a few hundred transitions, so each reports `training_status=bc_only_insufficient_transitions` — a property of the fixture corpus, not the pipeline: a single live cycle crosses the 1,000-transition threshold on its own and runs BC + DQN from the start. The optional `demo/run_dqn_demo.sh` reruns the same fixtures with the threshold lowered to 100 so cycles 2–3 run BC + DQN; it demonstrates that the stage executes, not that the policy improves. Adam optimizer state is not persisted across cycles (only network weights are); there is no vector database (`report_history` is a JSON file), and the past-report similarity model is a fixed-weight, untrained 7-feature logistic function. |
| §III-E Step 4 — Adaptive Evaluation Loop (two judges, three axes, conservative consensus, follow-up) | `evaluation.py` | implemented | `TIBLENDER_JUDGE_A_*`/`TIBLENDER_JUDGE_B_*` let judges use independent LLM deployments, matching the paper's design; if unset, both inherit the main LLM profile (a scale/cost simplification — set them explicitly to reproduce independent-judge deployments). `N_max=3`, conservative consensus (any `SKIP` suppresses the report), and structured `NEED_MORE_INFO` follow-up all match the paper. |
| §III-F Step 5 — Structured Report Generation (11 sections, JSON/MD/PDF/STIX) | `reporting.py`, `stix.py`, `pdf.py` | implemented | All 11 sections, the IoC exclusion rules (news/CDN/shortener/SNS URLs, 404/NXDOMAIN/clean results), and JSON/Markdown/PDF/STIX 2.1 exports are present, and match the released dataset record-for-record (e.g. `iocs.items[]` is `{type, value, extraction_type, platforms}`, confidence lives in `iocs_evidence`). Each recommendation's `horizon` (`immediate`/`short_term`/`long_term`) is requested from the model and otherwise derived deterministically from its leading verb; the released dataset leaves it optional (541 of 67,264 recommendations carry none), the runtime always populates it. **English-only report text** is enforced on both generation paths (see `PIPELINE_OVERVIEW.md` Step 5 for the guard/fallback mechanism); the committed three-cycle run rewrites nothing (`reports_rewritten: 0`). **Runtime → released record.** The released record exports the runtime report: `report_schema`/`report_text` carry the 11 released sections (`ttps` as MITRE ids, `sources` as one `{source_number, source_ref, summary}` row per post), and `source_posts.items[]` mirrors the released `{source_ref, platform, timestamp, text}`. The runtime's own `english_report` (`summary_en`/`key_findings_en`) is a root-level field, not one of the 11 sections, so it is not released. One shape difference: the runtime's `report_schema.iocs` rows carry `platforms`, while the released copy keeps 3 keys and moves platform attribution to `iocs.items[]` (see `dataset/README.md`). |
| §III-G Cross-Cycle Feedback — Trend detection (four axes) | `trends.py` | simplified | All four axes use the paper's thresholds (`W=168h`, `τ_sim=0.80`, `k=1.5`, `θ_ew=0.75`) — see `PIPELINE_OVERVIEW.md`'s Cross-cycle feedback row for the mechanism. **Volume** follows the deployed system's implementation (gated by `TIBLENDER_TREND_MIN_SIMILAR_SNAPSHOTS=4` and `TIBLENDER_TREND_VOLUME_MIN_POSTS=4`) rather than the paper's wording, with one deviation: `k` follows the paper (`1.5`) rather than the deployed default (`1.2`). On the bundled three-cycle fixtures only `EARLY_WARNING` fires — twice in cycle 1, twice in cycle 2 and twice in cycle 3 — since hashing embeddings rarely reach `τ_sim=0.80` across only three cycles of history, so `VOLUME`/`PROPAGATION`/`ESCALATION` stay silent. |
| §III-G Cross-Cycle Feedback — Dynamic query generation | `dynamic_queries.py` | implemented | LLM-backed or deterministic-template generation, matching the paper's design; capped per platform (`TIBLENDER_MAX_DYNAMIC_QUERIES_PER_PLATFORM=30`) and TTL-expired via `expires_at`. |
| Appendix — External Tool Inventory | `tools.py`, `tools_searxng.py`, `tools_virustotal.py`, `tool_fixtures.py`, `contract.py` | simplified | `PASSIVE_DNS_LOOKUP` uses VirusTotal resolutions, the provider the paper used (`VIRUSTOTAL_API_KEY`). `WEB_CRAWL` is recorded only for an explicit publisher-host allowlist (`fixtures/tools/recording_summary.json`'s `allow_crawl_hosts`); other hosts report `unavailable`. `SEARCH_ENGINE` uses SearXNG under Docker Compose's opt-in `live` profile, falling back to a recorded response otherwise. Coverage is measured, not assumed: every cycle tallies recorded-response replay per tool into `cycle_summary.json` (compared by `verify-sample`) — see `docs/REFERENCE.md`'s per-tool table and the 95 % floor the test suite enforces. A recorded `unavailable` counts as replayed: it is real recorded evidence of the provider's answer. |
| Appendix — LLM Agent Prompts and Output Schemas | `llm.py`, `llm_agents.py`, `llm_feedback.py` | implemented | Prompt structures and output schemas (P1 normalization, P2 clustering, P3 planning, judge prompts, P9 report sections) follow the appendix; only the model/provider identity differs (see the LLM row below). |
| §III-B–§III-F — LLM provider identity (applies to every LLM-backed step) | `settings.py`, `llm.py` | simplified | The paper used Grok 4 Fast (Microsoft Foundry) for generation and GPT-OSS-120B + Llama 4 Maverick as judges. This code accepts any OpenAI-compatible or Azure AI Foundry endpoint instead — neither specific model is required. Offline/credential-free runs use a deterministic heuristic stand-in (`metadata.generation_mode=offline_deterministic`, `metadata.llm_used=false`), never presented as a reproduction of the paper's LLM output. |
| §III-B–§III-F — LLM batch calls, truncation handling, and per-unit fallbacks (applies to every LLM-backed step) | `llm.py`, `llm_agents.py`, `llm_feedback.py`, `llm_fallbacks.py`, `evaluation.py`, `perspectives.py` | simplified | **Robustness deviation, recorded.** The paper does not specify request batching or per-unit fallback behavior; see `PIPELINE_OVERVIEW.md`'s "LLM chunking and per-unit fallbacks" for the mechanism (batch sizes, concurrency, retry-then-fallback, and the `llm_fallbacks`/`llm_fallback_reasons` accounting). A report touched by a fallback is marked `metadata.generation_mode=llm_partial`, scoped to only the reports that actually lost content — a partially deterministic report is never presented as fully LLM-generated. |
| §IV-B — 31-Day Operational Overview and §IV-C–§IV-G evaluation results | — | recomputed | The pipeline does not re-run the 31-day live deployment; `evaluation/run_evaluation.sh` recomputes its evaluation numbers from `dataset/` (see `evaluation/README.md`). For running the pipeline, the repository ships `fixtures/collectors/{x,reddit,telegram,discord}/` — anonymized, defanged excerpts of the released dataset (`raw_dataset/reports.jsonl`): 17 released reports, 107 posts, across 3 consecutive collection windows (see `fixtures/README.md`). Every fixture post keeps its released `source_ref`, and `fixtures/collectors/manifest.json` lists the selected report ids and the dataset file's sha256, so the bundle is cross-checkable against the released dataset. |
| Fixture design — bundled fixture IoCs (real campaign indicators rather than documentation-reserved domains and RFC 5737 IPs) | `fixtures/collectors/`, `tools/build_fixtures.py`, `tools/anonymize.py` | simplified | **Deviation, deliberate.** The bundled fixtures carry the (defanged) indicators of the campaigns they excerpt, not reserved domains. The fixtures are anonymized excerpts of the released dataset's own posts, and the recorded tool responses answer for those same indicators — substituting reserved domains would break that correspondence and stop exercising IoC extraction/confidence. Privacy is protected by anonymization instead (no handles, emails, phone numbers, or social-post URLs; every indicator defanged — see the next row). |
| Fixture design — named victims and clickable indicators in fixture text | `tools/anonymize.py` (`defang_text`), `tests/test_anonymize.py` | implemented | **Policy.** Every live indicator in fixture text ships defanged (`http(s)://host/...` → `hxxp(s)://host[.]tld/...`, bare domains → `host[.]tld`) for any host that is not a known publisher/vendor/platform domain, including `.onion` addresses; IPs, CVE ids and hashes are left untouched. This is behavior-neutral — `extract_iocs` refangs before extraction, so the pipeline sees the same indicators either way, and every recording key is unaffected. Organization names are kept where the organization is the reported subject of a public post, never a private individual. Platform-hosted URLs (`preview.redd.it`, `x.com`, `t.me`, ...) are removed outright rather than defanged, since they point back to one specific source post; post/author/guild/channel ids are regenerated deterministically and never shipped as real platform ids. |
| §III-E Step 4 — offline judge evidence score over the Step 3 aggregated context | `evaluation.py` (`_context_evidence_score`, `_is_actionable`) | simplified | **Retune, recorded.** The deterministic (non-LLM) judge scores the same evidence the LLM judge sees (confirmed-indicator count, indicator volume, tool success rate, perspective coverage), but keeps two legacy terms (independent-platform count, capped at 0.25; a +0.10 HIGH/CRITICAL severity bump) — without them, an offline cycle (where no live tool can succeed) would score every cluster on evidence it structurally cannot have. **Actionability is a precondition, not a score term:** those non-IoC terms alone clear the 0.62 bar, so a cluster with no indicator, CVE, or TTP is now suppressed rather than published empty, matching the paper's (§IV-F) definition of a report-level false positive. A report may still ship an empty `iocs` block when it carries a CVE or TTP instead — one report in the bundled run does. |
| §V-B — Ethical Considerations (no production databases/vector stores/worker pools) | — | not included (by design) | PostgreSQL/Neo4j/Redis/OpenSearch, the production API server and frontend, and the 32-worker investigation pool are out of scope for this reference implementation. |
